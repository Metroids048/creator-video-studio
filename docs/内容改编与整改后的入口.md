### 固定的是表现能力，内容仍要开发

第一次建立基准，先把确切原作的开头、展开、高潮/回报、声音、完整镜头关系与可编辑工程对应起来。没有完整工程时明确为“待建立对标工程”，不是已有模板。获准制作后先解决决定该形式是否成立的代表段，再完成对标基准；基准真实观看成立后才固定为换稿父版。历史失败不能因换个名字重新进入这一阶段。

固定项是该版本的构图规则、角色体系（若有）、镜头组织、完整动作机制、字体/材质、声音角色与节奏范围。可变项是题目、事实、台词/文案、素材及模板明确支持的对象与参数。不是把每个切点永远钉死：换稿长度、乐句变化可以在原语法内重排；若需要新动作机制、新镜头语言、不同画幅构图或新声音能力，就先报告这次已越过哪条边界，不暗中从零重写。

内容模块在这个范围内做具体工作：读取参考如何吸引并兑现，核新主题是否适配；把新稿逐段放到原事件/镜头能承载的位置，保持新的事实、解释或情绪回报；检查删改是否丢了用户要表达的东西。不能把“内容槽位”理解成换标题和名词，也不能为了模板容量把完整论证砍成口号。已有选题、开头和信息推进资源继续用于这些实际删改。

对标基准成立只说明这一版接近目标。可持续换稿还需要在同一父工程里换入实质不同的内容，包含原先最容易失败的一处，检查有无退化成重复字幕、走路填时长或丢失因果；真人认可单列。一个原题试验失败就先定位内容、表演或工程适配哪一层失效，不继续扩第二种形式。当前基准和换稿的质量资格均不因本次维护升级。

### 实际入口与边界

`intent` 对新主题、知识/故事/歌曲等新创作及已有完整稿返回 `select_reference_and_scope`，保留完整稿参与匹配；明确固定工程/指定模板时返回 `adapt_within_fixed_template`。参考研究、项目整改、已有素材编辑、恢复及返修保留各自入口。`template_match` 仍区分研究参考、工程储备与生产资格，不自动选中、不自动渲染，`next` 是交接建议而不是授权。

`content-plan` 保留原问题研究与历史失败反馈消费，返回的工作方法已改为模板内内容开发。执行仍走现有 `templates match → prepare → plan/make/workflow` 与父版路径；不新建平行生成器、不放宽市场或质量门槛。用户明确选定的参考可以研究、建立待验基准，不因此冒称市场或生产合格；没有可用模板时报告具体适配缺口。

### 已有 Vibe 成片：只读收编，不另开主链

2026-11-16 补上的消费入口是 `adopt-vibe`。它只复制已有成片、已认可音轨和字幕字节，登记到**显式隔离的 `--works-root`**。登记根不能位于或包含仓库 `works/` 树的任何位置，无论传入哪个 ID，在创建目录前就拒绝；不改源工程、`current.json` 或 owner 状态，不渲染。画幅、帧率、时长、帧数来自 ffprobe，唱词和时间来自 SRT；唱词是否等于实际演唱、逐句画面是否解释该句、成片内嵌音轨是否等于登记音轨，都记为未验。登记后走同一条 `status → review-prepare → review-save → export`。没有同版完整审阅时 export 拒绝，登记本身不是质量放行。

```sh
python3 scripts/studio.py --mode recovery --works-root /隔离登记根 adopt-vibe <短ID> /源工程 \
  --video <成片相对路径> --audio <音轨相对路径> --subtitles <字幕相对路径> \
  --version v0001 --request '<本版必须保留的原要求>'
```

锁定音轨 `inputs/approved-audio` 不在 `receipt.delivery` 里，改由统一的 `check_delivery` 按 `receipt.adopted.audio` 核实际哈希；status、review-prepare/review-status、export、发布包和重复登记都经过这一处，音轨被改动时全部失败。重复登记同一成片、音轨、字幕和原要求时复用；任一改变都拒绝覆盖，须换版本号。字幕时间超出成片、成片没有音轨、源在登记根内，都在生成版本前失败。Vibe 独立 CLI 仍不消费阶段冻结；收编只把已经做出的成片接进审阅和导出拦截，不把旁路工程改造成模板。

#### 整体消费链：哪一环由程序消费，哪一环仍是绕行

以《还没落地》为例。“程序消费”指真实入口读取并会因不符而失败；“绕行”指目前只靠 Codex 按文档执行，程序不拦。

| 环节 | 实际消费入口 | 仍存在的绕行缺口 | 恢复点 |
|---|---|---|---|
| 原要求与参考 | `adopt-vibe --request` 写入 brief `requirements`，`review-prepare` 把它带进审查包，审查包遗漏要求时 `manifest` 拒绝 | 参考原片与蓝叔等工程只在研究文档里；没有入口把“参考了哪一段、学了什么”绑定到这版 | 原要求原文、`current-request.json` |
| 方法/模板 | 代码路线由 `templates match → prepare → make` 消费 | Vibe 工程是在仓库主链外直接制作，没有模板绑定，`content_adaptation` 记为 `null` | 父版工程目录，只读 |
| 逐句画面 | 只有 SRT 时间轴被解析并核“不超出成片时长” | 唱词是否等于实际演唱、该句画面是否解释该句，都没有程序消费，brief 记 `unverified` | 父版 `film/lyrics-timeline.js` 与 SRT 哈希 |
| 锁定音轨 | `check_delivery` 按登记哈希核 `inputs/approved-audio`，所有入口共用 | 成片内嵌音轨是否就是这条锁定音轨，没有逐样本比对，记为未验 | `assets/还没落地-原曲小节剪辑.wav`，`e702a9e3…2c35` |
| 同版审阅 | `review-prepare` 抽全片 2fps 审查包；`export` 缺 `review-save` 结论时拒绝 | 连续正常速度声画观察只能由人或已验证的感知方式完成；程序不认证观察真实性 | 隔离登记根里的版本与审查包 |

当前下一允许动作只有一个：对隔离登记版本做同版完整看听，结论用 `review-save` 保存。没有这一步和用户认可，不 export、不发布、不覆盖父版。

## 从原文到实际镜头

Codex 从当前用户原文整理逐项 `requirements=[{id,text}]`，保留全文 `script`。新增 `purpose=self-media, route=code` 的工程，必须有 `content_adaptation`；普通技术工程和已有素材编辑仍保留原合同。用户不填写这些字段。

`content_adaptation.schema=1`，`script_sha256` 绑定全文 UTF-8 字节。每个 `units` 单元绑定：

- 稳定 `id`、实际 `shot`、镜头内 `[start,end]` 帧范围、所兑现的 `requirements` ID。
- `goal/before/action/after/reaction/camera`：目标、前状态、动作、结果、反应与镜头。`preserve/changes` 写清沿原作保留什么、为什么改。
- `source/target={asset,pointer,sha256}`：原生 JSON 的具体可消费单元。数组优先用 `/events/@稳定ID`，避免插入后指错对象。SHA 为 `stage_handoff.fingerprint(value)` 的规范 JSON 哈希，不是文件哈希。
- 原生 ZIP 可以加 `member`，直接读内部 JSON，不解压。`templates prepare` 请求里可用 `file` 代替 `asset`，绑定准备后的唯一同名输入。例如 `file=source-pack.zip, member=story.json`。外部原始 JSON 放进 `adaptation_inputs`，提供真实路径及全文件哈希。
- `capability` 为 `supported` 或 `unverified`；不支持的能力停止。未验证项只能进入 `production_stage=representative`。这些标签是范围声明，不会单独取得生产资格。

`templates prepare` 在临时目录内准备、冻结输入并核事件；成功才原子保存，失败不留下可误用的正式目录。已有目录拒绝覆盖。`plan/make` 的实际 `check_inputs` 再核全文、要求、源/目标、帧范围和镜头引用；纸墨再核生成 JS 中内嵌的事件数据。改变目标数据后，只更新文件哈希而不更新事件是不允许的。

这里强制的是可追溯数据关系。通用 JSON 中写了动作、甚至渲染器收到了该 JSON，都不证明动作真的被演出。复杂握持、转身、受力和喜剧反转仍没有成功方法；不能用“supported”自报解除已知限制。新稿必须先证明原代表性难点，不扩模板库凑数量。

## 沿已成型工程改编

先读原作与工程的完整事件、构图、角色、镜头关系和节奏，再把新内容对应进去。只有风格名、胶片滤镜、角色组件或路径插值不能称套用完整模板。

各引擎进入既有 `code_segment` 后，原生准备回执 `scene-source.json.consumption` 绑定实际输入、事件和准备后文件。方法证据的 `reused_components` 分别记录 `source_sha256/consumer_sha256`、`changes`、`shot/input/events`；允许有依据的适配差异，不再要求原文件与改编文件同字节。文件必须进入该镜头实际原生目录，单独复制到附件目录不能证明消费。

准备回执只证明提供给渲染器的内容，不能证明可见性、完整表演或移除对照效果。市场资料、可用工程、实际换稿记录分层；`templates list/match` 和目录页统一读取 `qualification`。标签分数只是检索线索。

## 局部上下文与必要失效

继续用原 `stage_handoff`，不另建执行器。事件所属阶段必须依赖全文及对应要求，镜头阶段必须依赖事件；遗漏 DAG 边会被拒绝。已有局部返修和父版复用保留，无关阶段不重开。

```sh
python3 scripts/studio.py scene-context /absolute/path/brief.json --shot shot-id
python3 scripts/studio.py workflow /absolute/path/task.json
python3 scripts/studio.py plan /absolute/path/brief.json
```

`scene-context` 只读返回当前、前后镜头事件及要求；先消费这些数据，避免为一个镜头重写整稿。它不替代完整故事审阅。已有字段归属、原生合同和确认操作见[阶段交接与局部返修](阶段交接与局部返修.md)。上述命令不产生新片；生产仍需当前明确授权。

## 观察与交付

审片包纳入逐项要求与内容承诺。当前**没有已接入并验证的 AI 连续声画感知适配器**，所以 AI 填 `ai_normal_speed_av/full/pass`、播放日志、抽帧或音频片段都不能取得全片放行；仍可用于诊断。不是换一个方法名即可通过。

真实人员完整正常速度观察时，`continuous_review.attestation` 指向包内证据 JSON，并纳入既有 evidence 哈希。它包含同版 `source`、与 reviewer.name 相同的 `observer`、`method=human_normal_speed`、全片 `range`、`speed=1`、空 `limitations`、实际 `modalities`（有音轨须 visual/audio）及真实 `statement`。Codex 不得冒填真人、代写不存在的回执。程序不能认证观察者诚实；缺真实观察就保持待验。单元测试中的 synthetic human fixture 仅验证程序合同，绝不能用于业务验收。

市场依据同核原证据中的指标、原帖身份、机制与完整观察记录，不接受仅在 routing 中改一个 full 标志。当前同样没有可用 AI 完整观察适配器，历史接触表不会自动获得资格。

包装新建使用 schema 4，继续消费同版视频审查；旧 schema 1–3 包保持只读核验，不自动升级当前交付资格。封面视觉或平台裁切若记录为已观察/有问题，该检查的 `images` 必须逐张含 `{index,sha256,observation}`，覆盖两张实际图片；观察要具体写字有没有碰框、缩略图能否读、实际裁切与未知项。程序只核绑定，不自动检测文字碰边。`publish-verify` 保留 `offline_ready` 表示文件完整，同时返回 `delivery_status/delivery_eligible`；被否决视频、待验和问题不能被旧包存在升级为合格。

已知反例须分清对象：《等消息》问号碰框在视频原帧中可见，原尺寸字幕完整；播放器底部裁切仍待定位，不改成“封面已修好”。完整业务质量、同版全片看听、用户认可分别保留待验。
