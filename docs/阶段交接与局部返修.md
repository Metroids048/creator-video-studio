2026-11-15实施。当前交付是入口维护及无媒体隔离验证，不是新片质量验收。记录仍在原 `workflow task.json`，不建立第二个运行器。JSON由Codex维护，用户只表达需求。

## 一个阶段交什么

每阶段绑定其拥有的brief字段、实际文件和直接依赖。确认保存字段值、文件SHA256、依赖回执；下游读取这些实际结果。`confirmed`只表示结构冻结，不表示内容、画面、声音或用户认可。

例如，已准备brief中的 `stage_handoff` 指向同一任务：

```json
{"stage_handoff": {"task": "/本作品/task.json"}}
```

在既有task中增加 `stages`，不要另建副本状态：

```json
{
  "action": "plan", "project": "example", "request": "用户原话",
  "brief": "candidate/brief.json",
  "stages": [
    {"id": "content", "needs": [], "fields": ["/request", "/script", "/title"]},
    {"id": "setup", "needs": [], "fields": ["/id", "/route", "/width", "/height", "/fps"]},
    {"id": "picture-one", "needs": ["content", "setup"], "fields": ["/shots/@one", "/inputs/@scene-one"], "artifacts": ["candidate/scene-one.js"]},
    {"id": "audio", "needs": ["content"], "fields": ["/audio"]}
  ]
}
```

这是字段示意，不可原样当完整制作brief。Codex根据实际brief覆盖全部字段，包括模板、策略、声音输入、时间线及许可等；遗漏由 `unowned_fields` 明确报错。每字段只属于一个阶段；列表使用稳定的 `@ID`，不能用易移动的位置序号。实际素材放入所属阶段的 `artifacts`，不能只冻结一串路径。输入路径搬迁及导出的派生字幕定时不算改内容，输入哈希仍受制作入口检查。

依赖表达真实影响：音频依赖文案，不依赖配色；精确定时依赖最终音源；单镜源文件分别归属对应镜头，共享角色文件归属共同上游。不要把全部步骤机械串成一条长链，也不要把所有镜头塞入一个大画面阶段后声称支持逐镜复用。

## 新片代表段与中断恢复

新自媒体整片由 `templates prepare`、新原生知识歌曲由 `native-knowledge describe` 把 `representative_review: 1` 写入 brief。将字段归属现有 task，在同一 task 创建 `representative-review` 阶段。选择最可能使观众听不懂或看不懂的短段。用本任务的实际文件、实际审阅入口和默认交付速度完成一次审阅。知识歌曲按 `song-start`、`representative-review`、`knowledge-song-preview` 的依赖顺序确认。

阶段的 `artifacts` 按顺序绑定观察 JSON、样片、实际审阅端回执；知识歌曲再绑定第四份 `song-audition` 报告。观察 JSON 记录 `media_sha256`、`capture_sha256`、`endpoint`、`speed: 1`、片内 `start`、`end`、`hard_case`、`observation`、`open_issues` 和有声样片的 `listening`。Google AI Studio 沿用现有原始捕获格式，记录页地址、输入文件指纹和已返回回复。知识歌曲首听须与样片使用同源编码混音，可直接读取样片中的音轨，也可交接等效解码文件。用 `workflow <task> --confirm-stage representative-review` 冻结证据；工作室整片与新原生入口都消费这一记录。程序校验文件、回执、时间窗和已记录问题，审美及是否有漏检依然以实际审查判断。

审片调用前保存同版文件和指纹，取得页面地址或任务编号时写回本作品状态，取得回复后立即保存原文。中断后先回读原任务、同版交接和现有回执。页面已有回复直接收取；结果未知时先查原任务再决定是否重交。启动或控制仍失败时保留样片、已完成阶段和原时间账，按实际可用入口恢复审片。相同反例在两次试法中都出现时，先查声音、镜头或入口哪一层有问题，确认新方案后在该短段验证。

原生 `compose` 用候选目录旁的临时目录写媒体、技术检查和回执，核完再整体提交。同一源码、画面、预审与媒体哈希的已完成候选直接复用。中断未提交时使用原命令和原路径可重试；有其他文件的目录或指纹不符时保留现场。早期的 brief 和已运行任务按原版本恢复。AVS、Vibe 经各自原生 CLI 时仍按其本地流程执行。

## 知识歌曲首听与同版否决

开工只制作用新唱法唱出的 6–12 秒混音短样，包含开场和最难咬字。工作流 task 可先引用只有作品 `id` 和 `content_format: "knowledge-song"` 的草案。建立 `song-start` 节点，`needs` 为空，`artifacts` 依次绑定唱法配置 JSON 和首听报告。唱法配置含本作品 `project`、`engine`、`version`、`voice`、`approach`、`settings`。

不提供歌词、画面或目标词，分别取得两路词句盲辨。再用 `python3 scripts/studio.py song-listening-prepare 混音 对标原片 --output 新目录` 准备匿名试听 WAV。可用 `--reference-start` 和 `--reference-seconds` 选择原片的可比片段。逐个把匿名音频交给同一实际听审端，先隐藏静音位置、原音身份和歌词。每份原始 JSON 答复记录 `silence` 为 `null` 或 `[起秒, 止秒]`，并给出 `vocal`、`arrangement` 的 `time` 和 `observation`。保留回执原文到 `capture-template.json` 对应 `samples[].response`，签明 `listener.kind` 为 `human` 或 `audio-model` 和具体 `listener.endpoint`。

校准后，由同一评审端以正常速度比较实际混音与对标音频，按实际演唱、乐句、音色、伴奏层次写出差异。原始对比 JSON 留在 `pair_response`，用 `candidate` 和 `reference` 指明对应匿名 ID。两项 `vocal` 和 `arrangement` 各含 `status` 与 `observation`，两项均有可定位观察并判为 `comparable` 才能确认。机器转写只用于词句检查。静音盲测检验评审端能否辨出已知变化，主唱与编曲仍由实际听审判断。

先运行 `python3 scripts/studio.py song-audition /本作品/首听报告.json`。报告字段如下，Codex 从本次实际素材登记。

| 字段 | 本次实际证据 |
| --- | --- |
| `mix`、`reference` | 实际混音和确切对标原片，各含 `file` 与 `sha256` |
| `targets` | `forms` 为同一句简繁等书写变体，`range` 为秒级范围。语义不同的近音词不可列为变体 |
| `observations` | 至少两个独立回执，各含 `observer`、`file`、`sha256`。原 JSONL 行含音轨 `sha256`、`reference_provided: false`、`text`、`start` 和 `duration`。仅实际全轨辨听的回执可用 `extent: full_file` 代替逐行时段。若工具用同源 WAV，记录 `decoded_input` 文件与 SHA256，入口校验采样率、声道和 PCM |
| `listening_source` | 同目录的实际听审回执 `file` 和 `sha256`。须以本版实际混音、干净对标、已知静音对照校验，并保留主唱与编曲原始对比 |
| `singing_method_sha256` | 本作品开工唱法配置文件的指纹 |
| `method_run` | 含 `method_sha256`、`mix_sha256` 和本版实际演唱运行回执 `source`，后者含同目录的 `file`、`sha256` |

运行 `workflow <task> --confirm-stage song-start`。唱法或听审未通过就停在短样并留原回执。该阶段可早于完整 brief 确认。通过后继续代表段及正式音轨，沿用同一唱法配置和对标来源，提交各自同版的实际听审。唱法变化时重开 `song-start`。整片预审 `audio_audition` 绑定冻结混音的报告与指纹。保留原来的 `mixed`、`earlier_mixed` 和 `crosscheck_mix.report` 时，报告须消费这些回执。预审 `editorial_comparison` 绑定同一原片的 `reference_sha256`，按 `hook`、`progression`、`payoff` 写清具体时间与差距。一次看开头、最难动作、结尾三个短段，核对连续接触和离场、因果、唱词和音效。保留实际联合视听端点、文件指纹、原始回应及恢复点；连接或上传超时时先核原标签、请求和输出。

阶段确认、正常制作及恢复入口共用上述报告。程序核回执、词句及记录中的判断，音乐表现与观看效果仍依赖实听和观看。用户明确否决时，通过 `review-save` 记录 `user_rejection`，保存确切 `video_sha256`、具体 `observation` 和带文件指纹的原反馈 `evidence`。原放行及导出保留供追溯。后续审查读回历史否决，原版 `export` 继续拒绝。

可查纸桥短样与《还没落地》的[原始听审回执](../works/paper-bridge-rerun-1119/receipts/song-start-listening-replay/listening-capture.json)和[制作入口拒绝回执](../works/paper-bridge-rerun-1119/receipts/song-start-listening-replay/replay.json)。历史《还没落地》的[正对照](../works/paper-bridge-rerun-1119/receipts/audition-replay/reference-control.json)只覆盖词句辨识。

## 实际操作

1. 新任务首次准备时，把任务引用交给 `templates prepare`；它会传入brief。确认有效内容、素材和模板后，用以下确认入口冻结。已有有效工程直接使用，重复prepare会拒绝覆盖已接入交接的工程。
2. 每次续做先读整个workflow，再只取当前阶段上下文。`decision=reuse` 直接消费已有文件；`work_on_this_stage` 只处理本阶段；依赖未就绪只回到最早失效依赖。P1–P6是按需调用的方法，不是每次必须重跑六次模型。
3. 局部返修保留父版及原素材；在候选副本修改允许字段，用具体反例重开其拥有阶段。重开只清除该节点与后继的确认，旧回执留在history；其他阶段保持。随后依次确认真实受影响产物，不重复确认无变化阶段。
4. 执行前 `plan/workflow` 检查候选；实际 `make/build/resume`、代码画面与声音返修、候选提交再次检查。修改了未获重新确认的上游，提交会失败。制作和交付仍须各自授权模式，本轮不运行。

```sh
python3 scripts/studio.py workflow /本作品/task.json
python3 scripts/studio.py workflow /本作品/task.json --stage picture-one
python3 scripts/studio.py workflow /本作品/task.json --confirm-stage picture-one
python3 scripts/studio.py workflow /本作品/task.json --reopen-stage picture-one --reason '具体缺陷和修改范围' --evidence /本作品/issue.json
python3 scripts/studio.py plan /本作品/candidate/brief.json
```

不带修改选项的workflow只读；confirm/reopen显式写本地交接记录，不派发模型、渲染或外部请求。重复确认有效阶段不重写记录。反例文件只核存在与哈希，真实性和语义必须由Codex实际核验。

代码画面/声音补丁仍沿原入口。Codex先在候选brief中整理与补丁一致的字段并更新交接，真实补丁入口再校验实际结果；当前没有自动从自然语言生成候选字段的程序。不得修改父版来消除冲突。`--stage`只返回本阶段和有效直接依赖，保留其他阶段ID；不会自动调用模型。

## 已接入及边界

| 范围 | 当前程序行为 |
|---|---|
| 新自媒体 `make` | `purpose=self-media` 的新任务必须带阶段交接；先核交接再创建作品 |
| 已接入任务 `workflow/plan` | 返回可复用、失效、下一阶段；有效计划不再重复模板match |
| 已准备brief直提、代码返修、resume、候选提交 | 检查实际消费的brief和文件；不能只凭旧task写了ready放行；返修不能移除父合同 |
| `templates prepare` | 保留任务引用；已有交接工程拒绝重复准备覆盖 |
| 旧任务与非自媒体通用brief | 不自动迁移；无引用明确 `legacy_untracked`，不宣称有新保护 |
| AVS、Vibe等独立原生CLI | 原生状态与门禁继续生效；制作本身未接入阶段冻结。已有成片可用 `adopt-vibe` 只读登记进隔离根，再走原 review/export；登记不覆盖源工程，也不证明质量 |
| 成片审查、包装与运营 | 仍走原同版review和发布包检查；包装/运营不是要求重新制作视频的阶段 |

文件哈希检查不是文件备份：被覆盖的素材不能靠回执恢复，必须保留父版/冻结输入。task引用目前是本机路径，跨机器或交付包恢复后需显式恢复原交接记录和路径；尚未做交接闭包打包。本层不阻止宿主自由调用其他工具，不保证模型绝不重复规划，也不判断未声明的语义依赖。未实测新片耗时、成本、画质或全链路收益，不给节省比例。

## 画面方法改变时保留声音与原生工程

2026-11-17《还没落地》的用户反馈表明：修好某个手势和裁切，仍可能保留整片的PPT视觉语言。遇到这类反馈，先定位实际空间、主体动作和镜头衔接缺失，重开画面阶段；不要重做已认可的声音、字幕或迁入。工程支持三维不等于作品必须改成三维，也不证明审美合格。实际方向、代表画面与失败保存在该作品的 [画面方向](../works/falling-studio-1116/画面方向.md) 和版本审查中。

`revise-picture` 现在允许把新的贴图、字体、数据模块或视频作为本镜头显式声明的 `sceneAssets` 加入返修：在 `visual.sceneAssets` 列出 ID，`inputs` 给出同 ID、kind、相对补丁文件的 path 和 sha256。新的主故事或 beats 入口仍须沿原声明替换；不能借新增素材改声音或替换其他镜头的既有输入。模块的相对导入也必须指向声明后实际落盘的素材名。所有文件先一起验证阶段交接、brief 和输入哈希，再复制冻结；预检不写缓存，父版不变。

同一次对话沿原链继续：具体失败 → reopen 画面 → 源文件与附属素材 → 实际代表运动段 → confirm → revise-picture → 同版 review-prepare / review-save；发现问题继续以该版为父版返修。音轨按成片内 AAC 数据、字幕按文件和定时分别核对。代表图只能排除构图反例，连续动作、转场和完整视听必须检查最终编码视频，不能用工程测试替代；本入口没有自动连续视听感知能力，不能据此承诺一次必出高分。

换画面方法前，先从当前请求和上一版列出必须保留的具体事件，例如地面与舱内对照、同一把标尺、同起点速度实验、接球后收回。换成三维也可能漏掉这些内容；v0007 的地面对照与标尺遗漏已保存为失败，不能把材质更好当作要求已兑现。代表段至少要包含完整的“动作前—条件改变—结果”，镜头在关键动作发生前到位，不能直到落球结束才看见地面，也不能靠说明文字补出画面没有表现的因果。

原生转场须同时检查画布和宿主页背景。《还没落地》v0006 在70.5秒淡出透明画布，露出宿主页的浅底而闪白；v0007 保持深色太空底，实际编码帧已验证该反例消失。该修法只适用于透明层露底，不作为所有转场的统一效果。中段则按正在解释的条件选择景别：共同起点实验保留全景，方向变化靠近飞船与向量，切线反证跟随离开的主体；连续运镜本身也不能代替内容推进。
