## 2026-11-15参考方法的实际使用

学习Fred具体反馈沉淀：每项回写实际时间码/现象→已知或待查原因→消费此规则的阶段/入口→原反例的复验，不把其56条规则整包加入所有Prompt。真实运营数据关联成片版本、平台和统计时间，交回下一次内容方向与编排；无数据不声称增长。研究、接线、生产和返修时间分开，原墙钟与失败不清零，不把缓存恢复速度当新任务稳定提速。

具体证据及边界见[七条参考与源码复盘](../../../docs/research/2026-11-15-原片源码与工作室复盘/研究总览.md)，执行沿现有[P1–P6](../../../docs/research/2026-11-13-后续制作方法与Prompt.md)及[制作流程](../../../docs/制作流程.md)。这些为当前Skill执行指引；除明确列出的CLI检查外，不声称已实现自动质量拦截或新增生产能力。


项目级制作流程复盘走 intent 的 framework，采用本 Skill 的逐任务归因方法，不要求发布包或不存在的平台数据，不自动生成下一题。每个相关任务分别保留：有效结果、失败/用户纠正、原因的证据与未知、实际消费入口、验证范围。检查 workflow/prompt/Skills 时追到准备输入、plan、实际素材检查与恢复，不能以增加文档或路由命中称已消费；当前方法入口见 `scripts/production_method.py`。方法绑定、模型是否遵循、成片质量和用户认可分别判断，跨题首版质量未实测就不写成已达成。

从 `self-media-studio` 路由 `analytics`；合同与输入示例见 [发布与复盘](../../../docs/发布与复盘.md)。

复盘报告同时保留发布包`quality`与平台数据状态。用户“还可以”、封面六七分，只按反馈范围记录，不扩大为整片视听、人审或流量认可。2026-11-14反馈见实跑目录的收尾复盘；视频质量问题回到视频依赖，封面问题回到研究/出图依赖，不通过只改包装掩盖片内问题。不改旧包或旧审查，不自动启动新制作。

按 [受众到复盘](../self-media-studio/references/受众到复盘.md) 将内容审查/实际用户反馈写成绑定 manifest 的 feedback.json，经 `--feedback` 传入 content-analyze/content-review；保存后必须实际用 `content-plan <复盘目录>/next-brief.json` 读取下一题。没有平台数据时保持 awaiting_data，内容审查不冒充流量复盘。回传选题为 research，保留原账号和一个主要变量、替代解释，不自动启动制作。

1. 绑定已核验发布包及其原视频 SHA256，不切换或修改制作版本。`content-analyze <包目录>` 为只读；没有真实数据时，保持 `awaiting_data`，没有指标与增长结论。
2. 用户有后台导出/截图或只读数据后，Codex 把原字段映射为文档中的 JSON，记录来源、平台、账号别名、平台作品 ID、发布时间、观察时间、窗口、时长与口径。缺失填 null，零才填 0；指标提取不确定时保留缺失及原因。不得用演示数据演示业务成功。
3. `content-analyze ... --metrics <JSON> [--baseline <JSON>]` 确定性计算。对照只纳入同平台、账号、内容类型、时长和观察窗口，每条作品一个快照；自我比较和重复样本不计。播放作分母的比率只是本项目描述口径，不是平台官方流量权重或综合分。
4. 对照真实内容、可核的评论与数据提出一个主要假设，写清依据、替代解释和下一条的一个改动。缺少曝光/点击/留存时，不凭播放量诊断封面点击或完播。无同类基线时只描述本条，关联不能证明因果。
5. `action=analytics` 的交接单核验后，`--mode delivery content-review <包目录> ...` 保存不可覆盖的 a 修订，快照与报告绑定原发布包；将短运营简报交回原制作入口，不自动改片或发起新制作。

方法参考 Easel 的快照/覆盖率纪律与 self-media-content-workflow 的复盘方法；本项目按自身合同实现标准库计算，没有安装它们的宿主或原脚本。上游版本与差异见已批准整合方案第9节。真实发布效果、专业判断与用户认可独立记录。
